# Dr.BIM 研发前关键详细设计基线 V1.0

> 状态：Approved Design Baseline / Implementation Artifacts Planned  
> 生效日期：2026-10-23  
> 目的：把架构审查发现的Owner、事件、状态、部署身份、知识拓扑和研发交付缺口收敛为一套可执行设计。本文不声称OpenAPI、AsyncAPI、DDL或自动化测试已经生成。

## 1. 适用范围

本文约束第一阶段Web SaaS、Core API、异步Worker、AEC知识运行时、Bridge、Desktop/Edge/MCP、Revit插件及公共平台服务。后续Tekla、Rhino、Blender和数字孪生复用同一对象与契约原则，不复制一套平行平台。

## 2. 产品与系统层级

|---|---|---|---|

### 2.1 客户端能力与本地建模边界

| 客户端 | 云端业务能力 | 本地BIM执行能力 | 到下一阶段的入口 |
|---|---|---|---|
| Web | 上传、解析、结果调整、人工确认、轻量三维预览、审核和云端结果版本确认 | 无；不得连接Edge、MCP或BIM进程 | 下载或打开Windows客户端 |
| Mobile | 与Web共享同一云端API、权限、项目状态和业务能力，并针对移动交互适配 | 无；不得创建、下发或执行本地建模任务 | 提示在Windows客户端继续 |
| Windows Desktop | 复用Next.js完整云端页面和业务能力，可从登录、建项和上传开始完成G1人工确认及不可变ResultVersion发布 | 有；通过Edge、MCP/任务适配器和原生插件执行 | 可直接继续，或承接Web/Mobile已完成G1确认且已发布ResultVersion的项目后创建任务 |

本地建模是云端结果确认后的可选后续流程，不是Web或移动端流程中的直接动作。正式建模任务只能在Windows客户端完成用户、项目、ResultVersion、设备、软件版本、模板、插件和本地保存位置校验后创建。`drbim://`只用于唤起客户端并定位项目，不承载完整任务载荷。

实现必须支持两种入口且在`ResultVersion`处汇合：`Web/Mobile确认结果 -> Desktop打开同一项目继续`，以及`Desktop登录/建项/上传 -> 云端安全检查与解析 -> 预览调整确认 -> 直接继续本地建模`。SaaS模式下第二种入口的上传和解析仍由Hosting Cell处理，只有BIM原生建模在用户本机执行；Customer Local模式可由Customer Local Cell及本地Worker处理前半段。两种入口不得复制项目、重复上传权威文件或生成平行版本链。

### 3.1 角色与职责实现基线

| 类型 | 固定口径 | 实现约束 |
|---|---|---|
| 客户基础角色 | OrganizationAdmin、ProjectOwner、Engineer、Visitor | 仅定义基础操作权限；前端显示名可本地化，稳定代码不得变化 |
| ReviewerDuty | 项目专业审核职责 | 必须绑定项目、产品、专业、阶段、范围和有效期；由MS-05消费并形成ReviewDecision |
| SignatoryDuty | 项目正式签发职责 | 必须绑定冻结交付对象并执行增强认证；由MS-10消费并形成DeliverySignOff |
| 第一阶段一般用户 | ProjectOwner + Engineer | 允许操作/参数确认及Desktop建模；禁止伪造独立ReviewDecision或DeliverySignOff |

`RoleBinding`不得保存签发范围来替代`ProjectDutyAssignment`；服务端不得仅依据前端菜单、Token中的历史角色字符串或“管理员”名称放行审核和签发。职责撤销、到期、账号停用、项目成员移除或职责范围变化必须发布高优先级失效事件，使Gateway、BFF、AI会话和待办队列立即刷新授权上下文。

### 3.2 SaaS实名、订阅、权益和计量实现基线

| 实现项 | 固定要求 |
|---|---|
| 实名门禁 | `IdentityVerificationCase`独立于Account；上传、可计费任务、购买/加购、开票、敏感导出和签发均在服务端检查`verified`且未过期 |
| 商业政策 | `CommercialPolicyVersion/PlanDefinition`使用`draft -> approved -> published -> retired`；未发布版本不得进入页面、订单、权限和测试 |
| 订阅状态 | `pending_activation -> active -> grace_period -> suspended -> expired/revoked`；`autoRenew=false`只表示不续订；到期可生成`locked_readonly`投影 |
| 产品权益 | 六条主要产品用稳定`product_code`逐项授权；附加权益保存主要产品、项目/工作空间、期限和政策版本 |
| 三类数量 | 一般用户席位、BIM厂商许可、Edge设备并发分别建模和校验，不得共用`seat_count` |
| 客户额度 | 预留、消费、释放和冲正写`CustomerQuotaLedgerEntry`，相同业务幂等键不得重复扣减 |
| 平台用量 | 文件、中间产物、版本、备份、CPU/GPU、Token、网络和BIM时长写`PlatformUsageRecord`，不自动扣客户额度 |
| 计量映射 | `MeterEvent`保存`meter_mapping_version`、客户单位和平台用量引用；账务只能追加/冲正，不得修改项目、任务和交付事实 |
| 未决商业规则 | 是否试用、单档/多档套餐、无限/固定席位标记`Pending Decision`；不得硬编码默认答案 |

最低研发制品包括：商业政策与权益DDL、状态机定义、OpenAPI/事件Schema、额度原子预留与幂等设计、双账本对账规则、服务端门禁中间件、只读锁定投影、策略发布后台和未决功能开关清单。

### 4.2 事件命名和载荷

事件统一使用过去式，最小信封包含：

```text
eventId, eventType, schemaVersion, producer,
aggregateType, aggregateId, aggregateVersion,
organizationId, projectId, authorityCellId,
occurredAt, correlationId, causationId,
```

正文、大文件、图纸、模型和完整建模计划不得直接放入消息；使用受权限保护的对象引用和内容哈希。

## 5. 关键状态转换基线

### 5.1 DrawingRevision

```text
AdmissionChecking
  -> AdmissionRejected
  -> QuotaReserved -> SessionIssued -> Uploading -> UploadedToQuarantine

UploadedToQuarantine -> SecurityChecking
  -> SecurityRejected -> Quarantined -> QuotaReleased
  -> SecurityTrusted -> SuitabilityChecking

SuitabilityChecking
  -> AwaitingInputMetadata
  -> SuitabilityRejected -> QuotaReleased/PolicySettlement
  -> Accepted -> DrawingRevisionCreated -> QuotaSettled -> Active
                                      \-> SettlementPending -> Reconciling

Active -> Superseded -> Archived
```

- 只有MS-02改变状态。
- Billing/Metering只改变额度预留与结算状态，不直接改变文件状态；MS-02消费结算结果推进可用性。
- `SecurityTrusted`之前禁止任何业务/技术解析；`QuotaSettled + DrawingRevisionCreated`之前禁止ParseRun。
- 单图框、PDF比例和受控ZIP Manifest属于Suitability，不得写入病毒扫描结果。
- 批量上传逐文件建状态机；重试使用`uploadBusinessId + itemId + attempt`，成功项不得重复扣减。
- 新编辑提交创建新Revision，旧Revision进入`Superseded`，不能原地覆盖。

### 5.2 ParseRun

```text
Requested -> Queued -> Running -> CandidatePublished -> AwaitingG1
                    \-> CancelRequested -> Cancelled
                    \-> Failed
                    \-> OutcomeUnknown -> Reconciling -> Running/Failed/Cancelled

AwaitingG1 -> G1Submitted -> PublishingResult -> Completed
          \-> CandidateSuperseded -> Running
          \-> Failed
```

- MS-03拥有解析业务状态；MS-07拥有调度任务状态，两者通过ID映射而非共享一张表。
- `StartParse`发生在G1之前；否则系统没有可供用户确认的识别候选。所谓“正式结果”指G1后发布的ResultVersion，不应另造一个G1之后才创建的“正式ParseRun”。
- 每次解析输出不可变`ParseCandidateRevision`；重跑产生新修订并使旧DecisionCase进入`CandidateSuperseded`，不得静默替换用户正在确认的候选。
- MS-05拥有G1决定和`ConfirmationSetSnapshot`，MS-03不得修改人工决定；MS-03只消费匹配的确认集发布ResultVersion。
- `Completed`必须在同一事务中生成不可变ResultVersion和`ResultVersionPublished` Outbox事件；任一步失败保持可重试的`PublishingResult`或进入对账，不得显示完成但无版本。
- G1提交使用`candidateRevisionId + decisionCaseVersion + idempotencyKey`并发控制；冲突返回明确版本差异，不采用后写覆盖。
- 迟到消息按`runId + attempt + seq + aggregateVersion`判定，不覆盖新尝试。

### 5.2.1 G1确认与ResultVersion

```text
ParseCandidateRevision
  -> DecisionCase
  -> ConfirmationCard[]
  -> ConfirmationDecision[]
  -> ConfirmationSetSnapshot
  -> ResultVersion
```

- `ConfirmationCard`必须引用候选对象、二维证据位置、来源通道、置信度、进入原因和影响范围，不能复制一份脱离来源的数据。
- 动作为确认、修改、丢弃、人工补录；每项记录操作者、时间、原值、新值、原因码和版本。批量操作逐项留痕，并生成汇总事件。
- 红色阻断项与黄色注意项均须清零后提交；颜色和阈值来自`ConfirmationPolicyVersion`，不得写死。
- 暂缓、稍后处理和草稿保存不改变未决状态；丢弃必须携带原因码，高风险丢弃还需影响确认。
- `ConfirmationSetSnapshot`是过闸时全量构件判定值的不可变快照，包含绿色自动接受项和全部人工决定，不只是“问题项列表”。
- `ResultVersion`至少绑定`drawingRevisionId/parseRunId/candidateRevisionId/confirmationSetSnapshotId/productLineCode/schemaVersion/unitSystem/coordinateSystem/parserVersion/modelVersion/ruleVersion/knowledgeReleaseId/contentHash`。
- G1辅助三维示意属于候选视图，失败时降级为二维证据和属性；正式GLB/glTF预览只读取ResultVersion，预览失败不反向篡改结果版本。

### 5.3 ModelingPlan

ResultVersion发布后，PreviewBuild与ModelingPlan是并行分支。PreviewBuild失败不改变ModelingPlan状态；ModelingPlan失败也不删除可用预览。

#### 5.3.1 PreviewBuild

```text
Requested -> Queued -> Running -> Ready -> Superseded
                           \-> Degraded
                           \-> Failed -> Queued（显式重试）
```

- MS-09拥有PreviewBuild和PreviewArtifact登记，Preview Worker只回传产物。
- 幂等键为`resultVersionId + previewProfileVersion`；同一输入和Profile重复请求返回既有Build。
- `Degraded`表示使用低精度Profile、部分属性或二维替代，不得冒充完整预览。
- PreviewArtifact只读引用ResultVersion，不能成为建模计划或交付签发的权威输入。

#### 5.3.2 ModelingPlan

```text
Draft -> Validating -> Frozen -> Superseded
                  \-> Rejected
```

- 只有MS-06写入。
- 只有Desktop授权会话可以发起计划；Web和移动端不得调用创建、冻结或启动接口。
- Frozen计划至少绑定ResultVersion、产品线、目标软件兼容范围、模板/族库Release、单位/坐标、TaskDAG、预期输出、CapabilityRequirement和内容哈希。
- 本地绝对保存路径、Windows用户名和本机敏感目录只保留在Desktop/Edge本地，不写入云端计划。
- 静态计划校验不依赖某一台当前在线设备；设备、许可证、插件、磁盘和目录权限在启动前预检。
- 输入ResultVersion、软件兼容范围、模板/族库Release或计划规则变化时生成新计划版本，不原位修改Frozen计划。
- PreviewBuild失败不是Rejected原因；ResultVersion失效则未派发计划进入Superseded，已派发计划进入影响评估而非静默换输入。

### 5.4 WorkflowRun与ModelRun

```text
Planned -> Queued -> Leased -> Dispatched -> Running -> Validating -> Succeeded
                    \-> CancelRequested -> Cancelling -> Cancelled
                    \-> OutcomeUnknown -> Reconciling -> Succeeded/Failed/Cancelled
                    \-> Failed
```

- 排队状态可立即取消；运行状态只能在插件安全点确认后取消。
- Edge失联不等于失败；对账前不能换节点重派同一写任务。
- 过期`fencingToken`回执只归档，不推进状态。

#### 5.4.1 写模型幂等、取消与断线对账

每条写模型命令必须携带：

```text
workflowRunId, bridgeTaskId, attemptId, commandId,
idempotencyKey, leaseId, fencingToken, sequenceNumber
```

- `idempotencyKey`标识同一个业务动作。插件或Edge发现相同键已经完成时返回既有回执，不重复创建或修改构件。
- `attemptId`标识一次技术执行尝试，不能替代业务幂等键；网络重连可以产生新尝试，但不得改变原命令语义。
- 插件持久化“来源对象ID -> Revit UniqueId”映射，并在完成、重连和对账时回读真实Revit元素。
- 排队状态立即取消；已派发未执行由Edge确认取消；运行中进入`CancelRequested -> Cancelling`，在事务批次安全点停止。
- 当前未提交事务可以回滚；已提交事务批次保留并在回执中列出，不得承诺整项任务自动回滚。后续清理由补偿计划或人工处理完成。
- Edge失联、Revit崩溃或保存结果不确定时进入`OutcomeUnknown`。MS-07/MS-08不得把同一写任务直接改派到另一设备，必须等待Edge本地账本、插件回查和模型指纹对账后再决定结果。

### 5.5 本地执行结果与平台制品状态

```text
Revit保存并回查真实元素
  -> ExecutionReceiptAccepted
  -> LocalModelExecutionRegistered
  -> ExecutionSucceeded

用户明确选择上传RVT/IFC/GLB/截图/报告
  -> MS-02上传隔离与安全检查
  -> ArtifactRevisionRegistered
  -> ArtifactAvailable
  -> Validated（适用时）
```

`ResultVersion`是Revit执行的已确认输入，不能在本地建模完成后再次生成同名对象。`LocalModelExecutionRecord`记录文档GUID或不透明本地模型标识、模型指纹、来源`ResultVersion/ModelingPlan`、Revit/插件/模板/族库版本、构件计数、必要`UniqueId`映射、保存结果、错误与签名回执，但不保存绝对本地路径或RVT正文。

`ExecutionSucceeded`只证明本地执行结果经过回执和对账确认；`ArtifactAvailable`才证明平台实际持有用户授权上传的文件；`Validated`表示对可取得Artifact或受信本地插件校核结果完成验证。未上传RVT时，平台可以展示任务进度、完成状态和回执摘要，但不得声称已存储、完整检查或可以在线预览最新RVT。

### 5.6 DeliveryPackage

```text
Draft -> InReview -> Approved -> SignedOff -> Delivered -> Superseded/Revoked
                  \-> Rejected
```

- 已签发包不可修改；变更生成替代包并保留关系。
- IFC只有在合同、Exchange Profile、权限和签发满足时进入正式包。

## 6. 模块依赖与调用规则

```text
Identity/Organization/Entitlement/Billing
                 |
                 v
MS-01 -> MS-02 -> MS-03 -> MS-05 -> MS-06 -> MS-07 -> MS-08 -> MS-09 -> MS-10
                    |        ^
                    v        |
                  MS-04 -----+
```

| 调用类型 | 允许用途 | 禁止用途 |
|---|---|---|
| 同进程应用接口 | 短查询、命令验证、事务外编排 | 调用对方Repository、共享可变实体 |
| 同步HTTP/gRPC | 跨部署单元短调用、能力查询 | 长任务等待、文件正文传输、循环调用 |
| Command消息 | 单一Owner异步处理 | 广播给多个竞争业务Owner |
| Event消息 | 事实发布、读模型、后续流程 | 用事件要求上游回写、多个生产者共用同名事实 |
| 对象引用 | 大文件、计划、结果和证据 | 永久公开URL、无哈希引用 |

CI需要阻断反向项目引用、跨模块Repository引用和循环依赖。

## 7. 部署单元与安全身份

| 部署单元 | 首期身份 | 主要权限 |
|---|---|---|
| Web/BFF | Web工作负载身份 | 调用公开应用API，不读业务数据库 |
| Core API | Core API工作负载身份 | 通过模块级连接池/角色访问对应Schema |
| Parse Worker | Worker身份 | 消费指定队列，读输入对象，写临时输出 |
| Knowledge Runtime | Knowledge身份 | 访问ArcadeDB和获批知识对象前缀 |
| Bridge Endpoint | Bridge身份 | 管理Edge长连接和加密任务包 |
| Desktop/Edge | 设备证书 + 用户委托 | 仅接收匹配设备、项目、租约的任务 |
| MCP Server | 本机服务身份 + 一次性任务令牌 | 调用白名单工具，不持有长期用户Token |
| BIM插件 | 签名插件身份 + 宿主进程上下文 | 在目标软件事务内执行有限命令 |

同一Core API内的MS模块不进行mTLS。跨进程、跨主机、跨Cell和设备通信必须TLS/mTLS，并结合用户/任务委托、ABAC、签名、nonce、时间戳和幂等键。

## 8. AEC知识三条运行路径

| 场景 | 知识位置 | 查询方式 | 禁止行为 |
|---|---|---|---|
| 在线公共/法域 | AWS AEC Core ArcadeDB | MS-04发送最小查询上下文，返回引用和证据 | 上传客户项目正文作为默认上下文 |
| 在线企业/项目私有 | Authority Cell私有ArcadeDB分区/检索端点 | 本地过滤和召回；只按策略发送最小证据参与融合 | 先全库召回再由LLM过滤 |
| 完全离线 | 签名KnowledgeRelease + 本地私有知识 | 本地全文/向量/图能力按已安装包降级运行 | 伪装成最新公共知识、离线回传项目正文 |

四种检索方式共享`knowledgeId/chunkId/releaseId/policyTag/sourceId`，但不要求所有知识位于同一物理ArcadeDB实例。

## 9. 容量建模方法

容量不按注册用户数直接推导，分为四个模型：

| 模型 | 核心输入 | 主要输出 |
|---|---|---|
| Web/API | 活跃率、页面请求、峰值系数、SSE连接数 | QPS、实例数、连接和缓存容量 |
| 文件/解析 | 文件数、大小分布、解析时长、并发、临时盘 | 对象存储、网络、Worker、队列上限 |
| AI/知识 | 查询量、Token、Embedding、Rerank和图遍历耗时 | GPU/CPU、并发、成本、降级阈值 |
| BIM执行 | 软件类型、席位、单任务时长、节点能力和许可 | Windows节点数、等待时间、拒绝/排队策略 |

5千、1万、10万和100万用户只能作为场景标签；在获得活跃率、项目量和任务率前不承诺具体硬件。Golden样本压测结果写入版本化Capacity Profile。

## 13. 与产品统一关系

产品统一基线定义客户可见范围、角色动作、三端体验、任务表现和商业政策；本文把它映射为唯一Owner、状态、命令、事件、部署身份和恢复路径。任何产品新增需求必须先回答：

1. 修改哪个产品线或内部能力？
2. 影响哪个权威对象和唯一Owner？
3. 新增Command还是已有Event的消费者？
4. 是否改变状态机、权限动作、数据区域或交付责任？
5. 是否需要新部署单元，还是仅新增模块/Adapter？
6. 是否影响现有Revision、RunTrace、审计和迁移？

无法回答以上问题的需求保持`Under Review`，不得直接进入开发任务。

产品分析事件还必须额外回答：它属于哪个阶段、是否仍在20%事件类型上限内、为何不能直接使用领域事实/审计/RunTrace/计费或可观测数据、谁是唯一生产方、何时关闭以及历史数据如何删除或匿名化。任一项没有答案时，事件保持`candidate/disabled`。
